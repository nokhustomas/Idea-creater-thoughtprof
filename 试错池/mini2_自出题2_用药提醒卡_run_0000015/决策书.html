用药卡的核心设计参数如何确定？

直接决定老人能否看清并正确用药，验收标准的核心来源

24pt+4.5:1方案（mind_first_principles）

为什么产出它：从老人视力数据倒推，80岁以上平均视力0.57，需大字高对比

优点
  • 满足验收硬性要求(info_005)(info_006)
  • 适配老人视力衰退现状(info_041)
  • WCAG无障碍标准合规
缺点
  • 大字体导致A4单页内容承载量受限
  • 可能需精简药品种类展示

因果链：老人视力0.57(info_041)→需大字+高对比→24pt+4.5:1为最低要求→验收必检

关键信息：
  • 80岁以上平均视力0.57±0.44(info_041)
  • 对比度4.5:1为WCAG正常文本最低标准(info_006)
  • 24pt为验收明确要求(info_005)

自适应放大型（mind_constraint）

为什么产出它：

优点
  • 可适应不同药品种类数量
  • 减少人工排版工作
缺点
  • 自动调整后仍需人工复核24pt要求
  • 增加脚本复杂度
  • 验收风险高

因果链：药品种类不确定→尝试自适应→仍需满足24pt→增加校验环节→与直接满足无优势

关键信息：
  • 王奶奶每日4种药(info_002)
  • 文件≤30KB限制(info_004)
怎么选：若老人视力正常且药品种类固定，选24pt+4.5:1；若药品种类可能变化且需灵活布局，可尝试自适应但需严格校验

时段标签采用哪些具体内容？

验收要求每日至少4个时段，且必须使用早/中/晚/睡前四选一

早中晚睡前（mind_first_principles）

为什么产出它：验收明确要求四个时段标签之一做主标题≥4次

优点
  • 完全符合验收标准(info_007)
  • 覆盖老人典型作息
  • 语义清晰无歧义
缺点
  • 仅4时段，若老人有特殊用药时间需另增列
  • 灵活性受限

因果链：验收要求≥4时段(info_007)→四时段覆盖典型用药时间→语义明确→满足要求

关键信息：
  • 验收要求：出现且仅出现早中晚睡前四时段之一做主标题≥4次(info_007)
  • 老人每日早中晚需服药(info_002)
怎么选：若老人常规早中晚3次用药，选早中晚睡前4时段；若仅有3个固定时段，仍需凑足4时段标签以通过验收

PDF生成采用何种技术方案？

决定能否稳定输出符合验收的PDF文件，影响最终交付

Puppeteer方案（mind_mece）

为什么产出它：HTML转PDF技术选型，渲染质量最高

优点
  • HTML与PDF内容完全一致
  • 支持CSS @media print控制
  • 支持A4尺寸精确设置(paperWidth:'210mm')
缺点
  • 需Chrome/Chromium运行环境
  • 服务器资源消耗较大
  • 无头模式调试困难

因果链：需求HTML直接打印为PDF→Puppeteer模拟浏览器渲染→page.pdf()输出A4→质量最高

关键信息：
  • Puppeteer支持paperWidth/paperHeight指定A4(info_046)
  • wkhtmltopdf需本地化字体处理中文(info_046)

wkhtmltopdf方案（mind_mece）

为什么产出它：传统服务器端PDF生成方案

优点
  • 命令行工具，集成简单
  • 资源消耗较Puppeteer低
  • 支持多种编程语言调用
缺点
  • 中文字体需本地化配置(info_046)
  • 默认不加载远程字体
  • CSS兼容性较Puppeteer差

因果链：HTML需转PDF→wkhtmltopdf基于WebKit→需配置字体路径→中文处理复杂

关键信息：
  • wkhtmltopdf中文乱码处理需指定系统字体路径(info_046)
  • PDF生成需退出码0且文件更新(info_008)
怎么选：若重视PDF与HTML完全一致且服务器资源充足，选Puppeteer；若追求轻量集成且熟悉wkhtmltopdf配置，选wkhtmltopdf

构建脚本使用何种编程语言实现？

影响脚本可读性、可维护性及与PDF生成工具的集成

Python脚本（mind_first_principles）

为什么产出它：PDF生成库丰富，脚本语言首选

优点
  • pdfkit、ReportLab、WeasyPrint等成熟库
  • 语法简洁易读
  • 跨平台兼容好
缺点
  • 需额外安装Python环境
  • 部分库依赖系统字体

因果链：需要生成HTML和PDF→Python库成熟→选Python实现构建脚本→合理

关键信息：
  • Python有pdfkit、WeasyPrint等库(info_053)
  • build.sh需从HTML生成PDF(info_003)

Shell脚本（mind_constraint）

为什么产出它：直接调用wkhtmltopdf命令行，流程简单

优点
  • 直接调用命令行工具
  • 无需额外编程语言环境
  • 与build.sh命名一致
缺点
  • PDF生成能力依赖外部命令
  • 脚本逻辑表达能力有限
  • 跨平台性弱(Windows需WSL)

因果链：需要生成PDF→调用命令行工具→Shell脚本直接执行→简化流程

关键信息：
  • 交付要求build.sh(info_003)
  • wkhtmltopdf为命令行工具(info_046)
怎么选：若团队熟悉Python且需复杂PDF处理逻辑，选Python；若追求轻量直接且环境已有wkhtmltopdf，选Shell
