| 原文 | 工作对应 |
| --- | --- |
| 道可道，非常道 | 对应「出方案」环节：任何方案都没法把客户原话完全描述清楚，写出来的方案永远不是真正的需求本身。接到一句话就动手做，必然跑偏；越早意识到这点，越愿意留缓冲。 |
| 名可名，非常名 | 对应「文件命名」和「接口命名」环节：人为起的名字都是临时约定，换个上下文就失效。验收命令里写的「读后感.md」「对照.md」是这一轮的名字，下一轮可能就改；不能把文件名当成永久真理。 |
| 无名天地之始 | 对应「接需求」刚开始的状态：需求还没被切分、还没起名时，是一片混沌。这时候硬塞标签只会扭曲事实。规矩是：先承认「还没名字」，再决定怎么命名，而不是反过来。 |
| 有名万物之母 | 对应「拆问」环节：一旦把需求拆成具体条目、起了名字，这些条目就会生发出后续所有动作（建文件、写代码、跑验收）。名字是母体，起了名就要为它负责到底。 |
| 故常无欲以观其妙 | 对应「debug」前的冷静观察：放下「赶紧修好」的冲动，先不带预期地看日志、看输入、看输出，才能发现那种「说不出来但就是不对劲」的微妙偏差。带着欲望去调，必带偏见。 |
| 常有欲以观其 | 对应「定位 bug 边界」环节：带着目标去查（想复现、想定位），才能看清问题的边界在哪儿、触发条件是什么。无欲看整体，有欲看细节，两者交替用。 |
| 此两者同出而异名 | 对应「联调」时的现象：同一个症状，研发说是接口问题，测试说是数据问题，验收说是环境问题——根因只有一个，命名却各说各的。这时候不能各执一词，要回到原始日志对齐。 |
| 同谓之玄 | 对应「复盘」环节里那些说不清但确实存在的经验：比如「不达标就重跑」「验收只认探针」这类不成文的默契，写不进文档但人人心里有数。暂无对应，因为这是机器工作里最玄的一类知识，目前只能靠一次次踩坑去沉淀，没法事先讲清楚。 |
